## 具体发现

### R1 P1 沙箱验收与环境重置之间缺少明确屏障

定位：[执行完成后的评测](architecture.md#51-实验与执行)、[数据环境与配置变更](architecture.md#54-数据环境与配置变更)，原文第 93、119 行。

文档要求 Evaluator 独立检查实际可用状态，同时允许同一沙箱在下一 Run 前重置，但没有规定谁采集最终环境状态、采集何时完成、何时允许释放沙箱。虽然写了“结束后保存证据”，仍不能确定这些证据是否足以独立完成规则验收。

具体风险：Run A 将副本设为 3 后结束，Run B 将同一环境重置为 1，此时延迟执行的 A 评测若查询实时状态，会误判；若只读 Agent 的总结，又不满足独立核验。

建议补充明确顺序：

```text
Run 执行终止
    → 可信环境验收器采集最终状态与约束检查证据
    → 按 run_id 和环境实例/代次封存
    → 允许释放及重置沙箱
    → Evaluator 从封存证据做离线规则/Judge 评分
```

验收器可作为环境 Adapter 的能力，不要求新增服务。若检查必须持续依赖活环境，就持续占用沙箱直至检查结束。采集失败、状态未知或待人工确认时不得自动重置并调度下一任务。应加入“A 延迟评测、B 已排队”的测试。

### R2 P2 执行调度与评测调度的契约尚未连通

定位：[模块边界](architecture.md#42-模块边界)、[进程与部署](architecture.md#43-进程与部署)、[状态与数据契约](architecture.md#6-状态与数据契约)，原文第 66、79、134、139 行。

Worker 被描述为“领取 Run”，同时又“按任务类型驱动执行和评测”，但 Evaluation 的独立生命周期没有说明如何排队、由谁创建、如何重试和防止结果被重复写入。图中也没有 Worker 驱动评测的关系。

建议选用最小工作项语义区分执行与评分：执行项关联 Run，评分项关联 Run 的封存产物版本、评测配置版本。Run 完成后由应用层/Runner 显式创建评分项，CLI 可针对原轨迹创建新版本评分。评分失败只重试评分，不重跑 Agent；同一评分项重复领取不能覆盖另一版结果。

同时统一报告职责：Evaluator 产出每 Run 的分项结果与失败依据，Runner 汇总跨 Run 的实验指标和报告。当前第 4.1 节将最终报告连到 Evaluator，第 5.1 节又交给 Runner，层次需要说明。

### R3 P2 三种上下文策略与结构化笔记的组合未冻结

定位：[上下文流](architecture.md#52-上下文流)，原文第 99、103 行。

三种策略名称明确，但“模型辅助笔记更新”被写成共用能力，未说明 Sliding Window 是否调用笔记模型、是否能读取历史派生笔记，以及 Memory/RAG 对照与 Context 对照如何分开控制。不同实现者可能构造出不同的“滑动窗口基线”，导致实验组无法复现。

建议增加策略能力矩阵，固定各组是否启用摘要、笔记、历史证据检索及模型辅助更新。事实性的任务约束和执行状态可以共用；由模型压缩获得的历史信息需要显式声明。若笔记三组都开，报告应标为“共享笔记条件下的三策略对照”；若只在部分组启用，它就是策略差异的一部分，不能将全部差异单独归因于压缩算法。

同样明确两个实验：Context 实验固定 Memory/RAG 条件，Memory/RAG 实验固定 Context 策略；两者无需立刻开展全部组合的笛卡尔积。所有辅助调用计入对应组成本。

### R4 P2 跨会话任务的 Memory 提交和后置任务启动缺少交接条件

定位：[Memory 与 RAG 流](architecture.md#53-memory-与-rag-流)，原文第 109、111 行。

已经要求序列按依赖顺序调度，但“任务结束后独立提出记忆候选”意味着 Run 结束与记忆更新完成不是同一事件。未规定下一个会话等待哪个条件，存在 B 在 A 的 Memory 尚未提交时启动、读到旧版本的设计歧义。

建议将“前置 Run 已终止”和“本次 Memory 更新已处理”分别记录。序列后置任务等待显式的记忆提交或跳过结果，并绑定实际读取版本。提取失败采用失败、跳过还是保留旧版，需要按实验配置固定，不能因执行时序而改变。普通独立任务不增加无必要的等待。

### R5 P2 恢复预算与状态转换规则需要从枚举补成行为契约

定位：[Run 状态](architecture.md#6-状态与数据契约)、[一致性与恢复](architecture.md#7-一致性与恢复)，原文第 137—158 行。

文档列出状态与恢复次数限制，但未明确失联后的 Run 转换、Attempt 与 Run 的终止关系、待确认期间的计时方式，以及 Token/成本/工具次数是否跨 Attempt 累计。若恢复只限制次数却每次重置调用预算，实验配置的预算含义会变化。

建议补一张状态转换表，列触发者、前置条件、允许转换与终止原因。明确 Run 级累计预算和每次 Attempt 的局部超时分别统计；等待人工确认的时间单列，并声明是否计入总期限。保留“完整重跑创建新 Run”的约定，不将可恢复中断先写成不可逆终态。

执行权版本和 Checkpoint 兼容性已作为待验证风险写入，不应误报成“已缺失旧 Worker 防护”；该项仍须在恢复模块任务中实测。

### R6 P2 工具引擎与 MCP Server 的职责需要分开描述

定位：[Tool Engine](architecture.md#42-模块边界)、[权限边界](architecture.md#8-权限与数据边界)，原文第 69、117、164 行。

目前把超时、重试、日志和权限统称给 Tool Engine，又要求“写工具最终校验”，但没有说明 MCP 服务端的资源白名单、版本检查和实际写入职责。两个 Agent 可能各自在客户端和服务端加入重试，形成重复请求或不同副作用判断。

建议规定：Tool Engine 管调用编排、Schema、调用预算、客户端执行日志与重试决策；MCP Server/Adapter 管实际查询或写入、服务端白名单与资源版本前提检查，返回可核验状态。声明哪些层允许重试、重试共享哪个逻辑操作标识。客户端校验提高早期反馈，服务端仍最终拒绝不允许的操作。

### R7 P3 总体图缺少职责节点 Word 图也有信息损失

定位：[总体图与模块表](architecture.md#4-总体架构与模块职责)，原文第 37—81 行；Word 第 3 页架构图。

Markdown 图未画出评测调度、Memory 更新写入和数据采集/环境验收职责；Planning 在范围、成本和里程碑中出现，却没有说明它属于 Runtime 的可切换执行策略。Word 图进一步省去了 Runtime → Model Gateway、Evaluator → Model Gateway 的直接关系，和 Markdown 图表达不完全一致。正文内容一致不等于两张图语义完全一致。

建议概要图只保留主要关系，再补部署图和关键时序图；将 Planning 明确归入 Runtime 策略，环境采集/重置/验收归入实验环境适配层。Word 与 Markdown 使用同一份图源生成，避免分别维护。无需新增微服务，也无需现在拆出全部代码目录。

### R8 P3 技术栈需要从名称清单补成职责映射

定位：[技术栈](architecture.md#91-技术栈与配置)，原文第 172—185 行。

技术范围已经完整，但 LangChain 当前只被列入 Agent 一行，不易看出它与 LangGraph、自建 Gateway 的关系；RAG 的拆分、索引和检索链路也主要靠读者推断。

建议补充：LangGraph 负责图编排与 Checkpoint；LangChain 的模型/检索组件在对应 Adapter 中按需复用，不替代项目自有契约；MCP 位于工具协议边界；pgvector 承担向量检索，知识文档分块及 Embedding 版本由 RAG 索引流程记录。数据库库、CLI 库、模型供应商、追踪平台等仍可在实施任务中选择，不必现在填满。

## 最小接口补充建议

下一版可以增加下表所示的语义边界，不要求立即规定字段或 Python 签名。

| 发起方 → 接收方 | 输入 | 输出 | 主要写入归属 |
|---|---|---|---|
| Runner → 工作项存储 | 冻结实验配置、任务及依赖 | 执行/评测工作项引用 | Runner 创建，Worker 领取 |
| Worker → Runtime | 可见 Task、Run 配置、执行权、恢复引用 | 终止结果与执行事件 | Runtime 执行状态，Worker 租约 |
| Runtime → Context | 当前状态、历史和候选引用、预算 | 模型输入、来源和派生版本 | Context 派生内容及组装记录 |
| Runtime → Tool Engine → MCP | 已授权工具参数、逻辑操作标识、前置条件 | 工具结果、外部状态与不确定性 | Tool Engine 调用日志，Adapter 外部写入 |
| 环境管理 → 验收采集 | Run、沙箱实例/代次、验收条件 | 封存的独立环境证据 | 环境验收器 |
| 应用层 → Memory 更新 | 前置 Run 产物、命名空间、初始版本 | 提交/跳过/失败和新版本 | Memory 模块 |
| 评测工作项 → Evaluator | 封存产物、独立依据、评测配置 | 分项评分与错误 | Evaluator |
| Runner → 报告汇总 | 指定版本的 Run 与评分集合 | 实验报告与统计口径 | Runner |

上述表为本次建议，尚未自动升级为用户已确认的接口决策。
