## 一、项目目标与规划基准

项目定位为 **Eval-Driven Agent Runtime：面向复杂任务的可评测、可恢复 Agent 执行平台**，以 K8s 故障诊断和沙箱运维任务作为验证场景。

项目重点建设三个核心模块：

1. **Agent Runtime**：可靠执行多步骤任务，支持状态持久化、Checkpoint、任务恢复和执行控制。
2. **Context Engineering**：在有限 Token 预算下选择、组织和压缩上下文，保护关键事实、约束和任务进度。
3. **Evaluation Harness**：自动评估任务结果、执行轨迹、成本和稳定性，支持策略对照与回归检测。

规划采用以下基准：

## 二、技术范围与模块职责

整体采用 **Python 模块化单体 + 独立 Worker**。沿用已有 FastAPI 工程，使用 LangGraph 组织执行流程、LangChain 接入模型与检索能力，PostgreSQL 保存任务和实验数据，pgvector 支持向量检索。

| 优先级 | 模块 | 本期建设内容 |
|---|---|---|
| P0 | Runtime | 执行状态机、ReAct 循环、步骤与预算限制、Checkpoint、恢复、取消和异常处理 |
| P0 | Tool Engine | Tool Calling、MCP 接入、参数校验、超时、有限重试、执行日志和幂等处理 |
| P0 | Context Engine | 候选信息收集、相关性选择、去重、Token 预算、摘要与工具输出压缩 |
| P0 | Evaluation | 数据集加载、批量执行、确定性校验、LLM-as-judge、轨迹评分、结果导出和回归比较 |
| P0 | 可靠性与观测 | Trace、用量及成本统计、故障注入、并发执行和错误分类 |
| P1 | Memory | 跨会话记忆、更新、去重、检索与任务隔离 |
| P1 | RAG | 带来源的向量检索；标准档增加混合检索与 Rerank 对照 |
| P1 | Planning | Planner / Executor 与简单 Reflection，和 ReAct 基线比较 |
| P1 | 部署 | Docker Compose；标准档提供 K8s 部署与可观测性集成 |
| P2 | 多 Agent、Web UI | 有余量时实现一个必要的委派场景或简易展示页面 |

模块之间遵循以下接口边界：

- **Model Gateway** 统一模型调用、结构化输出、用量和错误信息，目标支持两个真实模型后端切换。
- **Runtime** 调用工具与上下文策略，输出标准执行事件；不读取评测答案。
- **Context Engine** 接收任务状态、历史、工具结果、Memory 和 RAG 候选信息，返回符合预算的模型输入。
- **Evaluator** 读取执行轨迹、最终结果和独立保存的评测依据，输出分维度评分与失败原因。
- 模块级 API、Schema 和数据库结构，在各模块实施计划中确定；整体规划不提前固定字段细节。

业务数据来自固定版本的开源实验应用、实际产生的流量和可控故障注入。采集日志、指标、调用链及配置，形成可查询快照；保留少量真实环境端到端任务用于验证。黄金答案与注入信息由评测端单独持有。

**阶段验收：**

- 至少一个 K8s 故障任务能经过多次工具调用形成带证据的诊断结果。

- 步数上限、工具异常和基础状态恢复具备检查用例。
- 初始任务集可批量运行，导出确定性评分与失败原因。
- 可以按文档启动基础服务，并复跑该阶段案例。

| 周次 | 预算 | 主要任务与交付物 |
|---|---:|---|

| 第 6 周 | 19h | 完成摘要、结构化任务笔记与跨会话记忆；接入基础 RAG |
| 第 7 周 | 19h | 完成三种上下文策略、检索对照和实验版本管理；加入 Judge 与轨迹评测 |
| 第 8 周 | 18h | 扩充并检查数据集；完成初步策略对照、人工评分校准及阶段回归报告 |

三种上下文策略固定为：

1. **Sliding Window**：滑动窗口基线。
2. **Summary + Recent**：历史摘要与近期消息。
3. **Retrieval + Budget + Compression**：相关信息检索、预算分配与压缩。

**阶段验收：**

- 同一任务可通过配置切换三种策略，不需要修改 Runtime。
- 用户约束、未完成步骤、关键证据及反证有明确的保留和回取机制。
- Memory 支持跨会话使用，并验证更新、去重和任务隔离。
- RAG 结果有来源引用；评测集包含跨会话任务和检索干扰案例。
- 实验记录包含代码、模型、Prompt、策略及数据集版本。
- Judge 有明确评分标准和人工抽样校准记录。
- 标准档目标形成 80—120 条已检查样本，可由约 20—30 个模板及环境变体构成；模板数与样本数分别统计。

## 四、实验与最终验收

### 必须保留的实验

| 实验 | 组别与场景 | 核心指标 | 优先级 |
|---|---|---|---|
| A：上下文策略 | 固定模型和任务，比较三种策略 | 成功率、Token、总成本、平均与 P95 耗时、工具次数 | P0 |
| B：Memory/RAG | 全关闭、仅 RAG、Memory + RAG；包含跨会话任务 | 成功率、检索质量、无关信息引入和成本 | P0 |
| C：Planning | ReAct 对比 Planner / Executor + 简单 Reflection | 成功率、步骤、额外调用和成本 | P1 |
| D：恢复与并发 | 工具执行前异常、执行成功但未存 Checkpoint、并发超时与取消 | 恢复率、重复副作用、吞吐、P95 耗时、错误率 | P0 |

实验统一要求：

- 开发集与最终测试集按模板或场景分组，避免变体跨集合泄漏。
- 成功条件提前定义；确定性检查优先，Judge 辅助评价语义质量。
- 关键模型实验重复运行并报告波动，保留不利结果和失败样本。
- 总成本计入摘要、检索相关模型调用、重试、规划和 Judge，并分项展示。
- 同时报告每任务平均成本，以及总运行成本除以成功任务数的摊销成本；零成功时标为不适用。
- Mock 模型与真实模型负载结果分别报告。
- 不预设策略必须提高成功率或降低成本，以真实实验结果作为结论。

### 最终交付清单

- 可运行的 Runtime、Context Engine、Evaluation Harness 和工具接入。
- 集成 Memory、RAG 与至少两个真实模型后端。
- 标准档 80—120 条已核验样本及数据集说明。
- 上下文、Memory/RAG 两份详细实验报告和一份综合工程可靠性报告；标准档另含 Planning 对照结果。
- 自动化回归入口、完整实验配置、原始结果和失败案例。
- README、架构图、恢复时序图、关键设计决策和部署说明。
- 一个可复现的端到端 Demo。

核心模块和异常路径应有自动化测试。标准档争取关键路径覆盖率约 80%，但覆盖率只作辅助指标，必须同时提供真实故障与恢复验证。

### 工时不足或有余量时的调整

| 总投入 | 交付策略 |
|---|---|
| 180h | 优先交付 Runtime、三种 Context 策略、自动评测和可靠性验证；保留基础 Memory/RAG；缩减 Rerank、Planning、多 Agent 和完整 K8s 部署 |
| 225h | 按标准排期完成，包含 Planning 对照、完整实验和 K8s 部署 |
| 270h | 优先扩大验证深度，再选择深化 Memory、增加一个子 Agent 对照或增加并发测试 |

每阶段结束检查剩余工时。范围缩减优先发生在可选功能，不首先削减核心评测和故障验证。第 13 周仅用于缓冲、修复和补齐交付材料。

## 五、开发工具、协作流程与维护方式

开发工具采用用户已确定的组合：

**ChatGPT Plus 提供的模型与功能 + Claude Code 绑定 DeepSeek Flash API 按量计费。**

| 工具 | 主要职责 |
|---|---|
| ChatGPT Chat | 技术讨论、需求澄清、方案取舍、评测方法和实验结果分析 |
| Codex Plan | 阅读仓库，制定模块实施计划、接口边界、任务依赖和验收条件 |
| Codex | Runtime、Context、Evaluation 的关键实现；跨模块问题和独立 Review |
| Claude Code + DeepSeek Flash | 按已确定方案实现 Adapter、工具、API、RAG、配置、测试、文档及功能扩展 |
| CI 与人工验收 | 执行检查和回归，核对实验结果、演示及交付材料 |

具体模型以 Plus 中实际可选项为准，不将讨论记录中的模型名称、价格或额度估算作为项目实施前提。

开发流程：

1. 将阶段目标拆成可独立验收的任务，记录目标、接口、修改范围和完成标准。
2. 核心或跨模块任务先由 Codex 形成仓库内实施计划，再进入编码。
3. Codex 与 Claude Code 通过仓库文档交接；小任务可直接实现。
4. 同一工作目录串行修改；确需并行时使用独立分支和 worktree，明确文件边界。
5. 完成任务后运行对应检查，记录结果，按 Milestone 做关键变更 Review。
6. 每周更新进度、实际工时、问题和下周任务；每四周进行一次阶段验收。

仓库级执行细则见 [双 Agent 协作指南](collaboration/README.md)，统一标准见 [工程规范](engineering.md)，当前与目标边界见 [架构说明](architecture.md)。本地与 CI 共用 `scripts/verify.sh`；任务分配、版本化交接和 Review 由 [任务索引](collaboration/task-board.md) 进入。独立工作区在共享基线提交后创建，实际状态按任务卡记录。

项目运行时的模型 API 消费与 AI Coding 消费分别统计。运行时后端不受开发工具组合绑定，Plus 使用额度也不作为运行时 API 预算。三个月可沿用讨论记录中的 **¥900—1,500 资金预留**作为初步预算参考，实际根据账单调整。

本规划作为总排期入口，README 链接到本文；旧技术方案保留并标注历史参考状态。模块详细设计随对应阶段推进，不在整体规划中提前展开全部实现细节。
