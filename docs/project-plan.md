## 1. 项目定位

**暂定名称：OpsAgent Lab——面向故障诊断的 Agent 评测与上下文优化平台。**

建设一个可以查询监控、日志、发布记录和运维知识库的故障诊断 Agent；围绕同一批故障任务，持续评测并优化其准确性、证据质量、执行可靠性和成本。

将用户提出的两个方向合为一条主线：**评测体系负责验证优化是否有效，Context Engineering 负责提出和实现优化策略。** 业务 Agent 提供真实约束与演示入口，领域评测和上下文优化构成技术深度。

选择运维场景的原因：与已有故障可观测平台、集群运维管控平台经历相接，容易解释需求和工程取舍。个人项目使用自建实验环境、公开资料和可控合成数据；在求职材料中与公司项目明确区分。

本稿暂按每周投入 8—12 小时安排：第 3 个月形成可展示、可复跑的完整版本，第 4—5 个月按实验结果选择深化方向。实际投入、预算与业务场景偏好待后续确认，不影响先讨论方案。

## 2. 一个具体的使用流程

用户输入：“订单服务最近 15 分钟错误率上升，请定位可能原因，列出证据及下一步排查建议。”

1. Agent 检索服务手册、故障排查文档和历史案例，取得带来源的参考资料。
2. 根据已有证据选择查询指标、日志、服务依赖或发布记录，形成多轮工具调用。
3. 维护已确认事实、候选根因、反证和待验证事项，避免反复查同一条信息。
4. 输出候选根因及排序、证据引用、尚存不确定性和排查建议；证据不足时明确无法确认。
5. 平台展示执行时间线、评分、Token 消耗及估算成本，并支持与其他版本对比。

首版只做只读诊断。后续可在沙箱增加“提出修复方案—人工批准—执行—验证”的闭环，作为可选增强。

首批候选任务选 3 类：发布配置错误、数据库连接池耗尽、下游依赖超时。最终优先选取复用环境已能稳定产生的故障，不要求首月为候选列表补齐基础设施。逐步增加无故障、证据不足、干扰告警和多原因并发案例，避免只验证最顺利的路径。

## 3. 核心模块与技术落点

| 模块 | 实现内容 | 对应技术 |
| --- | --- | --- |
| 诊断运行时 | 状态图管理任务阶段，阶段内按证据选择工具；限制步数、时间和预算，支持中断与恢复 | LangGraph、ReAct |
| 模型与知识接入 | 模型适配、文档处理、检索链；先完成带来源的向量检索，再按失败案例增加关键词混合检索或重排 | LangChain、RAG |
| 提示与输出契约 | 分离角色、证据要求、工具使用规则、停止条件和输出 Schema；提示版本化，通过实验比较修改效果 | Prompt Engineering |
| 工具层 | 一个 MCP Server 暴露指标、日志、发布记录、知识检索等约 4—6 个工具；校验入参、限定查询范围、超时和错误分类 | MCP、Tool Calling |
| 评测模块 | 数据集版本、批量运行、规则评分、轨迹评分、Judge 校准、实验对比 | LLM-as-judge |
| 上下文管理 | Token 预算、压缩策略、结构化笔记、原始证据回取、可选子 Agent | Context Engineering |
| 服务与展示 | 异步任务、持久化、任务取消、审计、运行详情和实验报告 | Python、FastAPI、PostgreSQL、轻量页面 |

概念边界：ReAct 是根据观察反复决策和行动的执行模式；Tool Calling 是模型表达工具调用的机制；MCP 是工具和上下文服务的接入协议。它们分别解决执行、调用和接入问题。[MCP 官方架构](https://modelcontextprotocol.io/docs/learn/architecture)介绍了其客户端与服务端模型。

建议初期采用 Python 单仓库、API 进程与 Worker 进程，PostgreSQL 同时存任务、实验元数据并通过 pgvector 支持检索，Docker Compose 本地启动。原始轨迹先保存本地文件，云端演示时可迁入 OSS。Redis/独立任务队列按并发和恢复需求引入，不预先拆成大量微服务。

云端模型优先评估阿里云百炼中支持工具调用和结构化输出的模型；开发前核对具体模型与地域能力。[百炼 Function Calling 文档](https://www.alibabacloud.com/help/en/model-studio/qwen-function-calling)提供工具调用接入说明。先本地服务配合云 API，后续有演示需求再部署 ECS，不必先租 GPU。总预算由模型调用、Judge 调用、重跑次数、服务器与存储共同决定，先用少量任务实测再设月度上限。

## 4. 两个重点方向如何做深

### A. 可校准、可复跑的轨迹评测

评测对象是可观测事件：模型请求与返回、工具名称及参数、工具结果、状态变化、引用、耗时和用量，不以获取模型内部思维链为前提。

采用三层评测：

- **规则检查**：Schema 是否有效、工具参数是否合法、是否超时或越权、引用能否定位到实际证据。
- **结果评测**：根因判断、证据支持程度、建议可执行性、证据不足时的处理。已知注入故障优先用预设答案和关键证据检查，语义质量再由 Judge 辅助。
- **轨迹评测**：是否收集关键证据、是否处理反证、是否重复无效调用、工具失败后是否合理恢复。用证据覆盖和必要前置条件定义规则，允许多条正确路径，不强制唯一工具顺序。

先分别报告各维度，不急于合成一个总分。越权等硬性错误单独判定失败，不能被表达流畅度抵消。LangSmith 已提供规则、模型和人工等评测方式，可以复用追踪或实验基础设施；本项目自研重点放在运维任务数据、轨迹约束、校准及失败分析。[LangSmith 评测文档](https://docs.langchain.com/langsmith/evaluation)

去偏差采用可验证措施：匿名化模型身份；成对比较交换 A/B 顺序；统一评分标准并要求引用证据；抽样人工标注，统计人机分歧。对困难或分歧案例可增加不同模型家族的 Judge。另设长度偏好等探针，不能把“做了顺序交换”等同于消除所有偏差。位置、冗长和自我偏好可参考 [MT-Bench / Chatbot Arena 论文](https://arxiv.org/abs/2306.05685)。

可复现性分两种：

- **历史回放**：固定已有模型响应、工具响应和数据快照，检查流程与评分，便于定位回归；回放结果不用于声称新 Agent 的实时能力。
- **重新实验**：固定代码提交、依赖、数据集、知识库、提示、模型标识、参数和评分器版本，多次重跑并报告波动。temperature=0 不能保证云模型逐字一致；保存调用日期及平台能提供的版本信息。

### B. 用对照实验推动上下文优化

按以下顺序实现，每增加一种策略，都与上一版和基础版本对照：

| 策略 | 实现重点 | 要回答的问题 |
| --- | --- | --- |
| 基线 | 窗口允许时保留完整历史；超限时采用明确的滑动窗口策略并记录 | 不做复杂优化能达到什么水平？ |
| 工具结果裁剪 | 去重、按字段筛选、大日志分页，保留原始内容引用 | 能否在少丢证据的情况下缩减输入？ |
| 摘要压缩 | 按 Token 水位触发摘要，保留事实、反证与未完成事项 | 是否因摘要失真导致错误根因？ |
| 结构化笔记 | 固定字段保存事实、假设、证据 ID、时间、反证和下一步 | 相比自由文本摘要，是否更稳定？ |
| 子 Agent | 按需委派日志或变更分析，返回结构化发现和证据引用 | 在相同总预算下，收益能否覆盖额外调用成本？ |

原始证据独立保存；笔记保留来源与时间，支持冲突更新和回取；不同任务的记忆隔离。压缩过程必须保持工具调用与结果配对，避免产生无效消息序列。子 Agent 只作为第 4—5 个月的候选增强，不预设一定优于单 Agent。

摘要、结构化笔记和子 Agent 隔离上下文的设计参考 [Anthropic Context Engineering 文档](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)。本项目的价值在于实现、测量和解释取舍，不预先宣称提出了原创压缩算法。

## 5. 3—5 个月路线

| 阶段 | 工作范围 | 可检查的阶段产物 |
| --- | --- | --- |
| 第 1 月：闭环 | 3 类故障、约 30 个种子案例、RAG、只读 MCP 工具、单 Agent、轨迹记录、基础规则检查 | 从输入告警到带证据诊断报告可完整演示；能批量跑案例 |

| 第 3 月：优化与交付 | 工具结果裁剪、摘要和结构化笔记对照；超时、重试、恢复；部署与运行页面 | 可复跑实验报告、故障演示、架构与设计决策文档，形成求职展示版本 |
| 第 4 月：选择性深化 | 二选一优先：长任务上下文与子 Agent；或评测校准、偏差探针和困难案例 | 一项有充分证据的深入改进；无收益也保留实验结论 |
| 第 5 月：工程收尾 | 故障注入与负载测试、演示完善、技术文章、面试材料；有余力再补另一方向 | 完整交付包与实测指标说明 |

这些是建议规模，不以凑够案例数代替质量。种子案例先来自可控快照，随后补少量由自建服务真实注入故障产生的日志与指标。只在有足够人工检查能力时扩充数据集。

关键边界：黄金答案和注入配置由评测端持有，不暴露给被测 Agent，也不直接写入 RAG。开发集、Judge 校准集、保留测试集按故障模板和服务场景分组，避免同一模板换参数后跨集合泄漏。修改策略主要使用开发集，保留测试集用于阶段性验收。

## 6. 什么证据才能“经得住问”

优先形成 3 组实验：普通 RAG 问答对比工具驱动 Agent；无压缩/裁剪/摘要/结构化笔记对比；单 Agent 对比可选子 Agent。每次尽量只改变一个变量，固定数据和模型配置；上下文实验同时约束每任务总调用预算，计入摘要、重试和子 Agent 的开销。

核心指标：任务成功率、关键证据覆盖率、无依据断言率、平均及 P95 耗时、每任务 Token 和成本、工具错误及恢复率；另报告 Judge 与人工标注的一致性和顺序翻转率。成功条件逐案例预先定义，不能直接用 Judge 总分当作成功率。

阶段报告写明样本量、数据来源和划分、失败与超时计入方式。关键对比每案例建议独立运行 3 次起，报告均值与波动；需要区间时按案例聚合，避免把同一案例多次运行当成独立新样本。若人工标注只有自己完成，应写清这一限制。改进幅度一律待实测，不预填“提升 30%”等结果。

工程深度落在具体故障上：

- 工具超时、模型限流、返回内容格式错误时，区分可重试错误和永久失败，实行有限重试与退避。
- Worker 崩溃后，能恢复任务且不会无约束重复执行；持久化、任务幂等键与副作用处理分别设计。LangGraph 的 checkpoint 可作为恢复基础，但不自动保证外部操作恰好执行一次。[LangGraph 持久化文档](https://docs.langchain.com/oss/python/langgraph/persistence)
- 保存必要状态并验证取消、预算耗尽和步数上限；共享演示入口增加鉴权、任务隔离和审计。
- 将日志与检索文档作为数据处理，用少量注入样例检查其是否能诱导违规工具调用。
- 压测区分固定模型响应的服务承载能力和真实模型端到端表现，记录机器配置、并发、持续时间与错误率。

最终交付：可运行仓库、部署说明、架构图、数据集说明、实验报告、失败案例集、2—3 篇设计决策记录及短演示。后续是否公开仓库与文章另行决定，本次仅做本地方案备份。

未来简历可概括为“独立设计并实现面向故障诊断的 Agent 平台，构建轨迹评测与上下文优化机制”，但仅在对应工作实际完成后采用；量化数据注明环境、样本与测量口径，不包装为企业生产业绩。

## 8. 业务数据从哪里来

本项目需要的是“可查询的故障环境 + 任务说明 + 评测依据”，仅有问答对或孤立日志不足以支撑交互式 Agent 评测。

### 推荐的数据来源

| 数据 | 来源 | 用途与边界 |
| --- | --- | --- |
| 日志、指标、调用链 | 在开源演示应用中产生流量并注入故障，采集实际运行信号 | 核心评测证据；属于实验环境数据，不宣称生产数据 |
| 架构、配置、变更记录 | 固定版本应用的实际拓扑、部署配置、自行执行的变更记录 | 支持跨服务分析与时间对齐；隐藏注入脚本和直接泄漏答案的测试标签 |
| 知识库 | 环境服务说明、官方技术文档、自己验证过的排障手册 | 支持 RAG；保留来源及版本，不收录当前测试任务的答案 |
| 任务与黄金依据 | 测试人员记录的注入目标、前后表现、恢复验证、人工检查的关键证据 | 只供评测端使用；包含允许的答案粒度和证据不足时的预期行为 |
| 边界与扰动样例 | 在真实快照上作受控变换，或人工构造 | 验证超时、缺失、冲突、噪声等；标注合成来源，与真实采集结果分开报告 |

建议先验证 [OpenTelemetry Demo](https://opentelemetry.io/docs/demo/) 是否适合当前机器和目标场景。其 [Feature Flags 文档](https://opentelemetry.io/docs/demo/feature-flags/)列出支付失败、调用地址错误、服务高 CPU、队列积压等可控场景，能够减少从零实现业务系统的投入。

如果需要现成的交互评测编排，再评估 [Microsoft AIOpsLab](https://github.com/microsoft/AIOpsLab)：它包含环境部署、故障注入、负载生成、遥测导出与 Agent 接入接口，部署涉及本地 kind 或远程 Kubernetes 等选项。两者是候选复用路径，不要求同时部署；AIOpsLab 的集成成本也需要先验证，不预设开箱即用。

公开故障复盘可用于启发任务和补充背景知识，但通常缺少完整可交互现场，且模型可能已见过原文，不宜单独作为核心能力证明。纯日志异常数据集可做局部工具测试，不能直接等同于完整诊断任务。

### 从一次故障形成一个可用案例

建议流程：固定环境版本和负载 → 采集正常基线 → 注入故障 → 确认现象与证据 → 恢复并验证 → 保存任务包。

任务包包含 Agent 可见的问题、查询时间边界、日志/指标/调用链、拓扑、知识库版本，以及仅评测端可见的黄金依据。注入动作不自动等于有效根因标签：若故障没有生效、没有足够可见证据或存在混杂原因，应修正或剔除案例。

最初先做 5—10 个经过检查的任务，后续扩展至路线中的规模。不同负载、服务和时间配置可生成变体，但不能把同一模板重复计为多个独立故障类型。数据划分仍按模板与场景分组。

### 避免每次评测都重启一套环境

日常诊断实验使用“可查询快照”：工具根据服务名、时间范围、过滤条件、分页参数查询固定数据，Agent 每次重新决定操作并调用模型。同一个快照可以支撑不同调查路线。

这与第 4 节的历史轨迹回放不同：不能按原调用顺序返回固定答案磁带，再据此比较改变了查询路线的新 Agent。快照不支持的查询必须返回明确结果，不能由模型临时编造。涉及修复、动态状态变化或快照未覆盖能力时，使用隔离的实时环境评测。只读快照结论不延伸到自动修复能力。

## 9. 是否必须先造一个复杂 Agent

需要可运行、可插桩的被测 Agent，才能研究上下文策略对行为的影响；已有轨迹足以开始开发评分器，但不能完成上下文策略的端到端验证。评测与 Agent 应共同迭代，不采用“先投入两个月造业务平台，再开始评测”的安排。

推荐复用 LangGraph/LangChain 的运行与接入能力，自行实现薄基线：

`读取任务 → 构造上下文 → 模型选择工具或提交结论 → 执行工具 → 保存事件 → 继续或结束`

首批约 6 个工具：查询指标、搜索日志、查询调用链、读取拓扑、读取变更、检索知识。允许模型根据结果选择下一步，不把每个故障的正确调查顺序写进代码。先具备预算、步数和时间限制、可观测轨迹及基础错误处理；恢复和更细治理按路线继续补充。

将边界设计为可替换接口：Agent 接收任务与工具；Context Policy 根据状态和预算构造输入；Evaluator 读取标准事件与最终结果。评测器独立于被测 Agent，Agent 无权读答案或自行修改分数。先支持一个实现，后期有价值时再接第二种 Agent 或外部基线验证可迁移性。

首月建议：第 1 周验证一个环境、一个故障和数据采集；第 2 周形成工具与基线循环；第 3—4 周接入批量实验和最小评分。属于工作预算，不是完成承诺。若环境接入持续超出两周，优先缩减服务与故障类型，保证核心评测工作启动。

建议总投入占比：约 20% 用于环境、数据接入和薄基线，35% 用于评测，30% 用于上下文工程，15% 用于可靠性、展示与文档；实际记录投入，避免业务平台建设吞掉重点工作。

## 10. 如何验证复杂度足够

代码行数、工具数量和子 Agent 数量都不能直接证明任务难度。复杂度应由任务所需的信息依赖，以及基线的实际失败模式支撑。

| 难度层 | 示例约束 | 主要验证能力 |
| --- | --- | --- |
| L1 单服务直接证据 | 一种故障，指标或日志中有直接线索 | 工具接入、基础诊断与评分是否可用 |
| L2 跨服务证据链 | 上游报警、下游出错，需关联 trace、时间窗口和部署配置 | 多步调查与证据融合 |
| L3 竞争假设与反证 | 同期有无关发布，早期假设被后续证据推翻，文档存在版本差异 | 假设更新、反证保留、检索时效 |
| L4 长任务与恢复 | 跨时段调查、大量相关候选证据、工具暂时失败、调查中断续接 | 上下文取舍、结构化记忆与执行恢复 |

示例设计：结算失败，上游显示超时；同期发布看似可疑；进一步关联失败 trace 发现错误集中在某依赖；比较成功与失败请求及实际配置后才能确认原因。Agent 必须保留时间线和反证，才能解释为什么排除另一个候选原因。具体因果链以实验验证为准，不将故事直接当作黄金数据。

复杂度验收办法：先用直接 RAG/固定排查流程/简单 ReAct 做对照，观察哪些任务必须依据前一步结果改变后续查询；统计成功率、有效工具步骤、重复查询、错误定位点和上下文规模。若简单方法已能稳定完成全部任务，应承认基线足够，或补充现实中确有需要的新任务；不能仅凭设定工具步数认定任务复杂。

上下文实验保留短任务对照，重点加入有自然长程依赖的任务，例如早期得到的反证必须用于最终排除原因。按证据量和任务跨度分层，比较完整历史、合理检索/分页、滑动窗口、摘要、结构化笔记。较小 Token 预算可作压力测试，但须标注预算，不能通过故意塞无关日志或人为缩小窗口来制造唯一优势。

若压缩只降低费用而没有提高成功率，这仍可能是有效工程收益；若收益不稳定或造成证据丢失，应明确记录。项目价值来自可信结论和可复用能力，不以提前承诺多 Agent 更强或压缩必然提效为目标。
